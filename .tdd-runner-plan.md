## 3. Implementation Order (Outside-In TDD — Double Loop)

### Context-Aware Boundary
The test environment supports Jest (jest.config.mjs present). This is a pure repository stub story with no external dependencies, so the outermost practical boundary is the repository unit test layer.

### AC-001: findByDashboardId returns stubbed empty array

**Outer Loop — Acceptance Test:**
1. Write failing test: `findByDashboardId` should return `[]` for a given dashboard ID
2. Run test: confirm FAILS (method not found or returns undefined)

**Inner Loop — Implementation:**
1. Define `DashboardFilterPreset` type/interface (minimal fields: id, dashboardId, name, filter config)
2. Define repository interface with `findByDashboardId(dashboardId: string): Promise<DashboardFilterPreset[]>`
3. Implement in-memory stub that returns `Promise.resolve([])`
4. Run test: confirm PASSES
5. Write unit tests for edge cases: null/undefined dashboardId handling, multiple calls return new arrays (no shared mutable state)

### AC-002: save returns stubbed saved preset with generated ID

**Outer Loop — Acceptance Test:**
1. Write failing test: `save` with preset data (name, filters) should return object with generated `id`
2. Run test: confirm FAILS (method not found)

**Inner Loop — Implementation:**
1. Add `save` method to interface: `save(data: CreateDashboardFilterPresetInput): Promise<DashboardFilterPreset>`
2. Implement in-memory stub that:
   - Generates UUID for `id` (use `uuid` package or `crypto.randomUUID()`)
   - Stores preset in internal Map/array
   - Returns saved preset with generated ID
3. Run test: confirm PASSES
4. Write unit tests for edge cases: 
   - Multiple saves generate unique IDs
   - Saved presets can be retrieved by dashboardId
   - Input data is not mutated
